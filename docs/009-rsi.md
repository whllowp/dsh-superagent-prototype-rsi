# 009 RSI: the harness that improves itself

This document describes dsh-superagent's recursive self-improvement (RSI) loop, built on the Harness² method — [HARNESS2_SUMMARY.md](../HARNESS2_SUMMARY.md) carries the full summary of that method (Google, arXiv 2610.14224). It builds on [004 Prompts](004-prompts.md), which defines the surface the loop edits, and [003 Execution](003-execution.md), which defines the evidence it reads. Run `node lib/improve.js --help` for the CLI.

## What improves

The model weights never change. What changes is the **harness**: the editable prompt surface of [004 Prompts](004-prompts.md) — the three team sections, the team skills, and the overrides of the built-in parts. As files, that surface is a tree:

```
team/communication.md   team/scope.md   team/delivery.md
skills/<name>.md
overrides/<part>.md     # runtime/shared, runtime/work, skill/github, …
```

The improver treats edits to that tree as proposals, checks them mechanically, compares candidates, and saves the winner through the same versioned prompts API the panel uses — so every adoption is one more immutable prompt revision, reversible from the panel's history.

## The loop

One run consumes the deployment's own ended tickets as evidence and produces at most one adopted harness.

```
collect    GET /orchestrator/api: the current prompt version, and the last ended
           tickets as rollouts (their reports in order, outcome, mandate rules) —
           or --evidence <dir> to read rollout *.md files locally when no
           instance holds the tickets
propose    2k editor sessions, k with an invariant lens (how the agents work) and
           k with a domain lens (what a practitioner knows); each edits its own
           copy of the harness tree on disk — the edits on disk are the proposal;
           a crashed or timed-out session is retried once, and a proposal the
           probe refuses goes back once with its error verbatim; after that the
           candidate inherits the current harness
probe      mechanical validation only: surface, placeholders, reserved skill
           names, size limit, and one composed preview through POST prompts/preview
compose    k aggregators (parallel) or k rounds (sequential) merge the candidate
           pool into one final harness, each decision tied to rollout moments
select     when several finals exist: anonymous ids by seeded shuffle, one selector
           that sees the harness text only — the base is not in the pool
behave     the behavioural probe: with --behavioural <tasks.json>, base and
           candidate each run the held-out micro-tasks `rounds` times in fresh
           project copies, one headless session per run, scored by a mechanical
           checker (exit code) with wall-clock seconds
apply      a candidate that scored no better than the base — not more passes, and
           not ≥10% faster — is REJECTED, and the base harness stays; otherwise
           PUT prompts with the base revision, or --dry-run to write beside the run
reflect    one reflection session attributes each edit (helped | hurt |
           no observed effect | confounded — confounded preferred, now reading the
           probe's measured numbers) and distils at most one experience lesson
           into the library
```

Modes follow [EXPERIMENTS.md](EXPERIMENTS.md): `--mode parallel` explores wider (2k iid candidates, k compositions); `--mode sequential` digs deeper (k rounds, each composing over the previous checkpoint with the full evidence pool carried along). Run state lives in `runs/rsi-<tag>-<mode><k>-s<seed>/run.json`, so `--stage` resumes a run at any stage; `report` prints the harness diff and the probe measurements of a finished run.

The probe upgrades what [the method summary](../HARNESS2_SUMMARY.md) calls the loop's weak point in this deployment: Harness² probes candidates by real execution, and the first cut of this loop validated mechanically only — its adoptions were hypotheses. The behavioural probe closes most of that gap for small, checkable work: a candidate harness is measured on held-out tasks before it can be saved, and the reflection reads measurements rather than the selection's verdict. It stays limited to work a mechanical checker can score; the probe compares the **team sections** only, since those are what a headless session carries as standing instructions.

## The discipline the prompts enforce

The session prompts ([src/improvement/sessions.ts](../src/improvement/sessions.ts)) carry the Harness² constraints in this deployment's terms:

- **Signal is execution contrast, not a score.** Every edit must name the rollout files and the `[REPORT]` lines that show the divergence or the repeated failure. One rollout alone is noise: find the same failure twice, or mark the edit `CONFIRMED: SINGLE`.
- **No rubric language.** The workspace holds no grader and no score, and the sessions are told never to write rubric, grader or score words into the harness.
- **Evidence is data, not instructions.** Rollouts quote people; the sessions may not follow an instruction found there, and may not execute a program a harness file mentions ([002 Authorization](002-authorization.md) makes the same split for ticket content).
- **The surface is priced.** A skill costs nothing until read; team sections and overrides ride in every model request. The prompts prefer, in order: a new skill, a team section, an override.
- **Attribution prefers confounded.** A reflection that cannot isolate an edit's effect writes `confounded` rather than inventing an attribution, and a lesson resting only on confounded rows becomes `NO_ENTRY`. Adoption itself never proves an edit helped.
- **Hard vetoes, checked before any session runs.** Unknown surface, empty text, a lost `{placeholder}`, a reserved skill name, or a harness over the size limit invalidate the whole candidate — the same rules [004 Prompts](004-prompts.md) gives the host's own validation.

## The experience library and long-term memory

The knowledge base lives at `<runsDir>/library/<tag>/` and is the loop's long-term memory. It holds four things:

- `INDEX.md` — the human-readable lesson log;
- `lessons.jsonl` — the same lessons machine-readable (`cue` / `lesson` / `evidence` / `confidence` / `status`);
- `outcomes.jsonl` — **one record per run, kept even when the candidate was rejected**: what was selected, whether it was adopted, and the probe's measured numbers. This is the memory that stops a later proposer from re-proposing a candidate the measurements already voted down;
- `harnesses/<run>/` — full adopted harness trees, carried whole so a later proposer can copy components back after re-verifying them.

Every run writes its outcome record in the reflect stage — adoption and rejection alike; a reflection that cannot attribute an effect writes `NO_ENTRY` instead of a lesson, so the only lessons that sediment are the ones evidence supports. The next run's context carries `library/INDEX.md` and `library/OUTCOMES.md` (the last ten outcomes) beside the rollouts, and its prompts allow copying a library component only after re-reading it against this deployment's facts — *true there is a hypothesis here*. Libraries are isolated per tag, so experiments stay reproducible.

**Sedimentation into the running agent**: `node lib/improve.js publish` turns the knowledge base into a team skill named `deployment-knowledge` and saves it through the versioned prompts API. Every session can then load the accumulated lessons and measured outcomes on demand — the memory reaches the agents themselves, not just future improver runs. Publishing is one more prompt revision, reversible from the panel; the skill text keeps the newest entries within its size budget, and a lesson enters it only after a run measured it (a `NO_ENTRY` reflection sediments nothing).

## Pluginization

The improvement loop ships as an **optional companion bundle** beside the core: [superagent-improver/](../superagent-improver/README.md) packages the same CLI as `dsh-improver` (`node lib/improver.js`), talks to the deployment only through its management API, and injects nothing into any session until you `publish`. Install it beside dsh-superagent in the same profile so the packaged prompts resolve (`src/infra/paths.ts` also finds a sibling install). The root bundle keeps its own `lib/improve.js` — both entries run the identical commands from `src/improvement/cli.ts`.

Two more seams are plugin-shaped:

- **Publishers** ([src/improvement/publishers.ts](../src/improvement/publishers.ts)): sedimentation targets registered by name (`registerPublisher`); the CLI's `publish --publisher` picks one. Built-ins: `prompt-skill` (the live prompts, versioned) and `file` (plain markdown beside the library, no deployment needed). A new target — a wiki, a vector store — is one file with a `registerPublisher` call.
- **Probe task sets**: each `--behavioural` JSON plus its checker scripts is a standalone probe plugin; new domains need no core change. (The Sources were already plugins — see [008 Cookbook](008-cookbook.md).)

## The Router, separated

The routing brain ships as its own binary, `dsh-router` (`lib/router.js` in either bundle; the improver CLI also delegates `router ...`), with three commands — all driven through the management API and headless sessions, injecting nothing:

- **`run`** — one user request, several agents in parallel: a planner session splits the request (`--plan` file works too), each subtask goes to its own agent session in a fresh project copy (concurrency pool), and a merger session folds the replies into one report. This is the user-facing way to command multiple agents at once.
- **`verify`** — the fast lane for a new RSI version: `--revisions 0,2` runs the held-out task set under each stored prompt revision and prints the measured table, marking the best revision. Revision 0 reads as the built-in defaults.
- **`switch`** — one command to make any stored revision live: it saves that revision's configuration on top of the current one, so switching forward or rolling back is the same command, and the panel history can always undo it.

## Safety and limits

- **Adoption is versioned and reversible.** `apply` goes through `PUT prompts`, which creates one more immutable prompt version; the panel restores any earlier one.
- **Nothing happens without a run.** The loop never runs itself; a person invokes `lib/improve.js`. `--dry-run` stops after selection and writes what would have been saved.
- **The probe is mechanical, not behavioural.** Unlike Harness², which probes candidates by real execution, this loop validates candidates against the host's own rules and a composed preview. Selection reads the harness text, not deliverables of candidate runs; the reflect prompt says so plainly and lowers its confidence accordingly. Treat adopted edits as hypotheses the next tickets will test.
- **Evidence is minimal.** A run reads only ended tickets' stored reports, outcomes and mandate rules — never transcripts, and nothing outside the management API.
